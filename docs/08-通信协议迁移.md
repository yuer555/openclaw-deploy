# 08 - Gateway ↔ Agent 通信协议迁移

## 背景

原架构中 Gateway 通过 `docker exec` 调用容器内的 openclaw CLI（`--local` 模式），这要求 Gateway 和 Agent 必须在同一台宿主机上。为支持跨机房部署（Agent 容器分布在不同服务器），需要将通信方式迁移为网络协议。

## 方案选型

### 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| HTTP `/v1/responses` 同步 | 简单、标准 REST | 长任务超时不可控 |
| HTTP `/v1/responses` SSE 流式 | 标准 SSE、无超时问题、token auth 直接可用 | 需解析事件流 |
| WebSocket `chat.send` | 支持流式、实时 | 协议复杂、scope 权限受限 |
| Docker Remote API | 无需改代码 | 安全风险高、跨网络配置复杂 |

### 最终选择：HTTP SSE 流式 `/v1/responses?stream=true`

理由：
- openclaw 内置 OpenAI 兼容的 Responses API，支持 `stream: true` 参数
- SSE 流式连接保持活跃，不会因为 AI 思考时间长而超时
- Token 认证机制完善，与同步 HTTP 完全一致
- 事件格式标准（OpenAI Responses API 规范），解析简单
- 跨机房部署只需网络可达 + Token 一致即可

### 放弃 WebSocket 的原因

经过深入调研 openclaw WS 协议（版本 2026.2.26），发现其复杂度远超预期：

1. **握手协议**：需要 challenge-response 三步握手
   - 服务端发送 `connect.challenge`（含 nonce）
   - 客户端发送 RPC 请求 `{type: "req", method: "connect", params: {...}}`
   - 服务端返回 `hello-ok`

2. **协议版本**：当前版本要求 `minProtocol: 3, maxProtocol: 3`

3. **RPC 帧格式**：非标准 WebSocket 消息，需要特定格式
   ```json
   {"type": "req", "id": "<uuid>", "method": "connect", "params": {...}}
   ```

4. **connect 参数要求严格**：client 必须包含 `id`（值为 `"cli"`）、`mode`、`platform`、`version`

5. **`chat.send` 需要 `operator.write` scope**：token auth 模式下不授予此 scope，即使在 connect params 中请求也无效。尝试在 `openclaw.json` 的 `gateway.auth.scopes` 中配置也不生效。这是 WS 方案的致命障碍。

6. **维护成本高**：协议版本可能随 openclaw 升级变化，需要持续适配

## 实现细节

### 配置要求

每个 openclaw 容器（dispatcher + 5 个 agent）的 `openclaw.json` 需要：

```json
{
  "gateway": {
    "bind": "lan",
    "auth": {
      "mode": "token",
      "token": "<OPENCLAW_INTERNAL_TOKEN>"
    },
    "http": {
      "endpoints": {
        "responses": { "enabled": true }
      }
    }
  }
}
```

关键配置项说明：
- `bind: "lan"` — 监听所有网卡（`0.0.0.0`），允许外部访问
- `auth.mode: "token"` — 启用 Token 认证
- `http.endpoints.responses.enabled: true` — 启用 HTTP Responses API

### 调用方式

```python
# Gateway → Agent 的 HTTP SSE 流式调用
resp = requests.post(
    f"{agent_url}/v1/responses",
    headers={
        'Authorization': f'Bearer {OPENCLAW_INTERNAL_TOKEN}',
        'Content-Type': 'application/json',
        'x-openclaw-agent-id': 'main',
    },
    json={'model': 'openclaw', 'input': message, 'stream': True, 'user': session_key},
    timeout=(10, 2700),  # (connect_timeout, read_timeout)
    stream=True,
)

# 解析 SSE 事件流
for line in resp.iter_lines(decode_unicode=True):
    if not line or not line.startswith('data: '):
        continue
    payload = line[6:]
    if payload == '[DONE]':
        break
    evt = json.loads(payload)
    if evt.get('type') == 'response.completed':
        reply = extract_text(evt['response'])
```

SSE 事件流格式（OpenAI Responses API 规范）：
- `response.created` → 请求已接收
- `response.in_progress` → 开始处理
- `response.output_text.delta` → 增量文本片段
- `response.completed` → 完成，包含完整回复
- `[DONE]` → 流结束

### 环境变量

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `OPENCLAW_INTERNAL_TOKEN` | 所有容器共享的认证 Token | `openclaw-internal-secret` |
| `OPENCLAW_GATEWAY_URL` | Dispatcher 地址 | `http://localhost:18789` |
| `AGENT_*_URL` | 各 Agent 容器地址 | 见 `.env.*.example` |

## 踩坑记录

### 1. 宿主机 launchd 服务端口冲突

**现象**：HTTP 返回 `405 Method Not Allowed`，WS 返回 `token mismatch`，但容器内部测试正常。

**根因**：openclaw 安装时自动注册了 macOS launchd 服务（`ai.openclaw.gateway`），在 `127.0.0.1:18789` 监听。该进程优先于 Docker 端口映射接收请求，导致所有从宿主机发出的请求打到了错误的进程。

**排查过程**：
```bash
# 发现两个进程监听同一端口
lsof -i :18789 -P -n
# com.docker  73378  ...  TCP *:18789 (LISTEN)        ← Docker
# node        86106  ...  TCP 127.0.0.1:18789 (LISTEN) ← 宿主机 openclaw
```

**解决**：
```bash
# 卸载 launchd 服务
launchctl bootout gui/$(id -u)/ai.openclaw.gateway
# plist 位置：~/Library/LaunchAgents/ai.openclaw.gateway.plist
```

**教训**：在 macOS 上开发时，如果 Docker 端口映射的服务行为异常，优先检查是否有宿主机进程抢占了同一端口。`lsof -i :<port>` 是最直接的排查手段。

### 2. Agent 容器缺少 Token 认证配置

**现象**：之前使用 `docker exec openclaw ... --local` 调用时一切正常，改为 HTTP 后认证失败。

**根因**：`--local` 标志会绕过 gateway 认证。Agent 容器的 `openclaw.json` 原本没有配置 `gateway.auth`，只有 dispatcher 有。

**解决**：在 `Dockerfile.agents` 的 CMD 中为所有容器统一配置 Token 认证和 HTTP 端点。

### 3. Docker 构建缓存导致配置不生效

**现象**：修改了 `Dockerfile.agents` 的 CMD，但容器内 `openclaw.json` 仍是旧配置。

**根因**：Docker 构建缓存命中了旧的 CMD 层。

**解决**：`docker compose build --no-cache <service>`

## 跨机房部署架构

```
┌─────────────────────┐   HTTP SSE /v1/responses   ┌──────────────────────┐
│   机房 A (Gateway)   │ ◄──────────────────────── │   机房 B (Agents)     │
│                     │    stream=true              │                      │
│  Flask 网关 (:8000) │ ──── Token Auth ────────► │  agent-operation     │
│  Dispatcher (:18789)│                            │  agent-product       │
│                     │                            │  agent-development   │
│                     │                            │  agent-testing       │
│                     │                            │  agent-service       │
└─────────────────────┘                            └──────────────────────┘
```

要求：
- 机房间网络可达（Agent 容器的 18789 端口可访问）
- 所有容器使用相同的 `OPENCLAW_INTERNAL_TOKEN`
- Agent URL 配置为实际可达的 IP:端口
