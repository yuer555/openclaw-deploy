# 08 - Gateway ↔ Agent 通信协议迁移

## 背景

原架构中 Gateway 通过 `docker exec` 调用容器内的 openclaw CLI（`--local` 模式），这要求 Gateway 和 Agent 必须在同一台宿主机上。为支持跨机房部署（Agent 容器分布在不同服务器），需要将通信方式迁移为网络协议。

## 协议对比报告

基于 openclaw 2026.2.26 实际测试，对三种候选协议进行了完整评估。

### 协议概览

| 维度 | HTTP 同步 | HTTP SSE 流式 | WebSocket |
|------|-----------|--------------|-----------|
| 端点 | `POST /v1/responses` | `POST /v1/responses` + `stream:true` | `ws://.../ws` |
| 连接模式 | 请求-响应，一次性 | 长连接，服务端单向推送 | 全双工持久连接 |
| 认证 | Bearer Token | Bearer Token | Token + 三步握手 |
| openclaw 配置 | `responses.enabled: true` | 同左 | 默认开启 |

### 1. HTTP 同步

```python
resp = requests.post(f"{url}/v1/responses",
    headers={'Authorization': f'Bearer {token}'},
    json={'model': 'openclaw', 'input': msg, 'user': session_key},
    timeout=2700)
data = resp.json()
```

- 调用最简单，一次请求拿到完整回复
- AI 思考期间连接空闲，受 `timeout` 限制
- 复杂任务（agent 调用工具、多轮推理）耗时可达数分钟，极易超时
- 中间代理（nginx、云 LB）通常有 60-120s 空闲超时，无法调大

### 2. HTTP SSE 流式

```python
resp = requests.post(f"{url}/v1/responses",
    headers={'Authorization': f'Bearer {token}'},
    json={'model': 'openclaw', 'input': msg, 'stream': True, 'user': session_key},
    timeout=(10, 2700), stream=True)

for line in resp.iter_lines(decode_unicode=True):
    if line.startswith('data: '):
        evt = json.loads(line[6:])
        if evt['type'] == 'response.completed':
            reply = extract_text(evt['response'])
```

- 连接保持活跃（持续收到 delta 事件），不触发空闲超时
- 事件格式标准（OpenAI Responses API 规范）
- 每次请求独立连接，天然隔离，无需过滤其他 session 的事件
- Token 认证与同步 HTTP 完全一致，零额外配置
- 断开后可重连同一 session 继续对话

### 3. WebSocket

```python
# 步骤 1: 连接，收到 challenge
ws = websockets.connect(f"ws://{host}/ws")
challenge = json.loads(await ws.recv())  # connect.challenge

# 步骤 2: 三步握手
await ws.send(json.dumps({
    "type": "req", "id": str(uuid4()), "method": "connect",
    "params": {
        "client": {"id": "cli", "mode": "cli", "platform": "linux", "version": "2026.2.26"},
        "auth": {"type": "token", "token": token},
        "protocol": {"minProtocol": 3, "maxProtocol": 3},
        "nonce": challenge['data']['nonce']
    }
}))
hello = json.loads(await ws.recv())  # hello-ok

# 步骤 3: 发送消息 — 失败
await ws.send(json.dumps({
    "type": "req", "id": str(uuid4()), "method": "chat.send",
    "params": {"message": msg, "sessionKey": session_key}
}))
# → 错误: missing scope: operator.write
```

- 握手协议复杂：challenge-response 三步，参数格式严格（`client.id` 必须为 `"cli"`，必须含 `platform`）
- 协议版本绑定：当前要求 `minProtocol: 3, maxProtocol: 3`
- RPC 帧格式非标准：`{"type": "req", "id": "<uuid>", "method": "...", "params": {...}}`
- `chat.send` 需要 `operator.write` scope，token auth 模式不授予此 scope
- 连接是全局的，收到所有 session 的事件，需按 `sessionKey` 过滤
- 协议版本可能随 openclaw 升级变化，需要持续适配

#### WebSocket scope 问题详情

`chat.send` 需要 `operator.write` scope，这是 WS 方案的致命障碍。尝试过的绕过方式均失败：

| 尝试 | 结果 |
|------|------|
| connect params 中请求 scopes | 无效，仍报 `missing scope` |
| `openclaw.json` 配置 `gateway.auth.scopes` | 无效，重启后仍报错 |
| `auth.mode: "none"` | 报 `DEVICE_IDENTITY_REQUIRED`（需要设备配对） |
| 使用 `owner`/`admin`/`human-relay` 角色 | 无效，只有 `operator` 角色可用 |

### 关键差异对比

| 维度 | HTTP 同步 | HTTP SSE | WebSocket |
|------|-----------|----------|-----------|
| 超时风险 | 高（空闲连接被中间件断开） | 低（持续有数据流） | 低（心跳保活） |
| 实现复杂度 | 最低（~5 行） | 低（~20 行，解析 SSE） | 高（握手 + RPC 帧 + 事件过滤） |
| 认证复杂度 | Bearer Token | Bearer Token | Token + challenge + 严格参数 |
| scope 要求 | 无 | 无 | `operator.write`（token auth 不可用） |
| 会话隔离 | 天然隔离（per-request） | 天然隔离（per-request） | 全局连接，需手动过滤 sessionKey |
| 断线恢复 | 不适用（一次性） | 重连 + 同 session 重试 | 重连 + 重新握手 |
| 流式输出 | 不支持 | 支持（delta 事件） | 支持（assistant 事件） |
| 中间件兼容 | 好 | 好（标准 HTTP） | 一般（需 WS 支持） |
| 协议稳定性 | 稳定（OpenAI 标准） | 稳定（OpenAI 标准） | 私有协议，版本绑定 |

### 结论

| 方案 | 可用性 | 推荐度 |
|------|--------|--------|
| HTTP SSE | 完全可用，已在生产部署 | 推荐 |
| HTTP 同步 | 可用，但复杂任务超时 | 仅适合短任务 |
| WebSocket | 不可用（scope 限制） | 不推荐 |

### 最终选择：HTTP SSE 流式 `/v1/responses?stream=true`

## 实现细节

### 配置要求

每个 openclaw 容器（dispatcher + 5 个 agent）的 `openclaw.json` 需要：

```json
{
  "gateway": {
    "bind": "lan",
    "auth": {
      "mode": "token",
      "token": "<OPENCLAW_INTERNAL_TOKEN>"
    },
    "http": {
      "endpoints": {
        "responses": { "enabled": true }
      }
    }
  }
}
```

关键配置项说明：
- `bind: "lan"` — 监听所有网卡（`0.0.0.0`），允许外部访问
- `auth.mode: "token"` — 启用 Token 认证
- `http.endpoints.responses.enabled: true` — 启用 HTTP Responses API

### 调用方式

```python
# Gateway → Agent 的 HTTP SSE 流式调用（单次）
def _call_openclaw_sse(url, message, session_key, timeout=2700):
    resp = requests.post(
        f"{url}/v1/responses",
        headers={
            'Authorization': f'Bearer {OPENCLAW_INTERNAL_TOKEN}',
            'Content-Type': 'application/json',
            'x-openclaw-agent-id': 'main',
        },
        json={'model': 'openclaw', 'input': message, 'stream': True, 'user': session_key},
        timeout=(10, timeout),
        stream=True,
    )
    resp.raise_for_status()

    final_data = None
    for line in resp.iter_lines(decode_unicode=True):
        if not line or not line.startswith('data: '):
            continue
        payload = line[6:]
        if payload == '[DONE]':
            break
        evt = json.loads(payload)
        if evt.get('type') == 'response.completed':
            final_data = evt.get('response', {})

    return extract_reply_text(final_data) if final_data else ''
```

SSE 事件流格式（OpenAI Responses API 规范）：
- `response.created` → 请求已接收
- `response.in_progress` → 开始处理
- `response.output_text.delta` → 增量文本片段
- `response.completed` → 完成，包含完整回复
- `[DONE]` → 流结束

### SSE 断线重试

openclaw 在服务端按 `sessionKey` 持久化会话，与连接无关。SSE 断开后重连同一 session，agent 仍保留完整上下文。

```python
# 带重试的调用包装
def _call_openclaw(url, message, session_key, timeout=2700):
    try:
        return _call_openclaw_sse(url, message, session_key, timeout)
    except (ConnectionError, ChunkedEncodingError) as e:
        logger.warning(f"SSE 连接断开: {e}，尝试重试")
        retry_msg = "请重复你刚才的回复，不要做任何修改，原样输出即可。"
        return _call_openclaw_sse(url, retry_msg, session_key, timeout)
```

重试策略：
- 捕获 `ConnectionError`（网络中断）和 `ChunkedEncodingError`（流式传输中断）
- 向同一 session 发送"请重复上次回复"，agent 基于会话上下文原样输出
- 仅重试一次，避免无限循环

### 环境变量

| 变量 | 说明 | 默认值 |
|------|------|--------|
| `OPENCLAW_INTERNAL_TOKEN` | 所有容器共享的认证 Token | `openclaw-internal-secret` |
| `OPENCLAW_GATEWAY_URL` | Dispatcher 地址 | `http://localhost:18789` |
| `AGENT_*_URL` | 各 Agent 容器地址 | 见 `.env.*.example` |

## 踩坑记录

### 1. 宿主机 launchd 服务端口冲突

**现象**：HTTP 返回 `405 Method Not Allowed`，WS 返回 `token mismatch`，但容器内部测试正常。

**根因**：openclaw 安装时自动注册了 macOS launchd 服务（`ai.openclaw.gateway`），在 `127.0.0.1:18789` 监听。该进程优先于 Docker 端口映射接收请求，导致所有从宿主机发出的请求打到了错误的进程。

**排查过程**：
```bash
# 发现两个进程监听同一端口
lsof -i :18789 -P -n
# com.docker  73378  ...  TCP *:18789 (LISTEN)        ← Docker
# node        86106  ...  TCP 127.0.0.1:18789 (LISTEN) ← 宿主机 openclaw
```

**解决**：
```bash
# 卸载 launchd 服务
launchctl bootout gui/$(id -u)/ai.openclaw.gateway
# plist 位置：~/Library/LaunchAgents/ai.openclaw.gateway.plist
```

**教训**：在 macOS 上开发时，如果 Docker 端口映射的服务行为异常，优先检查是否有宿主机进程抢占了同一端口。`lsof -i :<port>` 是最直接的排查手段。

### 2. Agent 容器缺少 Token 认证配置

**现象**：之前使用 `docker exec openclaw ... --local` 调用时一切正常，改为 HTTP 后认证失败。

**根因**：`--local` 标志会绕过 gateway 认证。Agent 容器的 `openclaw.json` 原本没有配置 `gateway.auth`，只有 dispatcher 有。

**解决**：在 `Dockerfile.agents` 的 CMD 中为所有容器统一配置 Token 认证和 HTTP 端点。

### 3. Docker 构建缓存导致配置不生效

**现象**：修改了 `Dockerfile.agents` 的 CMD，但容器内 `openclaw.json` 仍是旧配置。

**根因**：Docker 构建缓存命中了旧的 CMD 层。

**解决**：`docker compose build --no-cache <service>`

## 跨机房部署架构

```
┌─────────────────────┐   HTTP SSE /v1/responses   ┌──────────────────────┐
│   机房 A (Gateway)   │ ◄──────────────────────── │   机房 B (Agents)     │
│                     │    stream=true              │                      │
│  Flask 网关 (:8000) │ ──── Token Auth ────────► │  agent-operation     │
│  Dispatcher (:18789)│                            │  agent-product       │
│                     │                            │  agent-development   │
│                     │                            │  agent-testing       │
│                     │                            │  agent-service       │
└─────────────────────┘                            └──────────────────────┘
```

要求：
- 机房间网络可达（Agent 容器的 18789 端口可访问）
- 所有容器使用相同的 `OPENCLAW_INTERNAL_TOKEN`
- Agent URL 配置为实际可达的 IP:端口
